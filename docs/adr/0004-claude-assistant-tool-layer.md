# Let Claude reach the lab only through audited, observer-side tools

The owner asks Claude about the lab, or asks it to act, from a panel beside the wall. Claude runs on the observer, not in the browser: the server calls the Claude API (`claude-opus-5-5`, adaptive thinking, server-side refusal fallback) through the official `anthropic` SDK's tool runner, and the page polls the run's trail.

Claude never receives lab credentials or a shell. It gets a small set of tools, each of which the observer executes and records: the tool, its input, the account or command used, the time, and the exact text returned to the model. The owner reads that text under "Evidence sent to Claude". Read-only tools use the `lab_observer` account. A search must aggregate, and `_raw` fields are dropped from search and REST results, so raw event text stays on the workstation. REST reads refuse search-job and stored-password endpoints, and secret-looking text is masked in container logs.

`show_screen` is how Claude shows the owner what it is doing: it adds a display step that the page turns into focusing that component and opening the named Splunk Web path in the live view the owner already controls. For guided walkthroughs Claude also works inside that same live view. Because the view is served from the observer's own origin, the owner's open page carries out Claude's `read_screen`, `click`, `type_text` and `select_option` requests in the iframe the owner is watching, highlights each element it touches, and posts the result back. Nothing runs without an open page following the run. The reading leaves out Splunk's event list (raw event text) and password values. Clicks whose label or target suggests a change (Save, Delete, Enable, submit buttons) and Enter in form fields wait for approval. The owner can pause or take over, which holds Claude's next action, and hand back. Claude proposes a walkthrough's steps for the owner to start and calls `checkpoint` after each step, which waits for Continue.

The only tool that changes the lab, `container_action` (podman start, stop, restart), blocks until the owner approves a card that states the reason, the expected effect, and the cleanup. Declining, stopping the run, or 15 minutes without a decision returns that outcome to Claude and changes nothing. Each approved change is recorded as an observation, and the run ends with a summary that lists any container still stopped. Splunk changes use a second tool, `splunk_change`, offered only when the owner has created the dedicated `lab_operator` account (admin role, password in a mode-600 `operator.json` written by the lab's `observer.sh operator`). It sends one splunkd POST or DELETE per approval, refuses stored passwords, the admin and observer accounts, authentication providers, and server control, and masks secret-looking fields in the reply before Claude sees it. Its approval card names the account, and the cleanup Claude gives is listed in the run summary.

The API key is entered in the panel and stored in a mode-600 file in the observer's config directory (or taken from `ANTHROPIC_API_KEY`); it is never returned by the API. The SDK is an optional dependency, so the rest of the observer still runs on the standard library.

Claude Code can also work on the lab from a terminal conversation, with its own access and the owner's approvals in the terminal. So the owner can watch that work the same way, `observer.terminal` appends steps (screens shown, notes, actions and results) to a run in the observer's store marked `origin: terminal`. An open page polls for the most recently updated run and follows it while it is live. These runs cannot be continued through the API panel, because their history is not a Claude API conversation.

A run is also the unit of evidence. When it starts, the observer records every component's state, Splunk version and installed app versions. Each step keeps its own evidence. `capture_evidence` and each walkthrough checkpoint save a screenshot, taken by the headless browser as `lab_observer`, into the run's own folder (`runs/<id>/` under the data directory), separate from the 48-hour preview cache; screenshots are never sent to the model. `record_verdict` stores pass, fail or inconclusive with the step numbers that support it. Unpinned runs and their folders are deleted after 30 days; pinned runs stay until unpinned. The owner's own browsing in live views is not recorded; only run steps are evidence.
